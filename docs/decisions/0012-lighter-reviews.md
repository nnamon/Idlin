# 0012: Lighter reviews and tests, and a fast gate

Date: 2026-11-27. The operator on #266: "Try to maximise progress please.
Overly long reviews and pedantic busywork test suites all contribute to
progress inefficiency. We should get things right in a reasonable and
appropriate amount of time." Changes sections 4 to 6 of `AGENTS.md` and steps
4 and 6 to 8 of `process/cycle.md`.

| Decision                                                                                                                                                                                                                                                                     | Rejected alternative                                                                            | Why                                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| One code review per pull request. A finding blocks only for a real defect: a crash, lost data, wrong behaviour a viewer would see, broken determinism or snapshots, a security hole. Missing tests and style are listed and do not block, except for determinism and saving. | Every finding fixed or answered before the merge, with a new review after each substantial fix. | Rounds of review on points no player would notice slowed every pull request down.                                                                      |
| Blocking findings are fixed once and the pull request merges without another full review, unless the fix itself was large or risky.                                                                                                                                          | A full re-review after every fix.                                                               | A small fix to a named defect is easy to check against the finding; a second full review mostly finds new non-blocking points.                         |
| Core logic (simulation rules, saving, the server) needs a test that would fail without it. Viewer code needs one where there is something to compute. Builders don't prove each test fails on revert.                                                                        | A failing-without-it test for every change, checked by reverting.                               | The simulation and saving are where a silent mistake costs most. Tests of each visual detail were slow to write and mostly restated the code.          |
| The watch judge looks once per `look` pull request. Only a hard fail or a "worse" verdict blocks; the rest becomes follow-up issues.                                                                                                                                         | Re-judging after each round of polish.                                                          | A judge's quota is better spent on new changes than on the same one again.                                                                             |
| The gate aims at about a minute on CI. Long sweeps run a sample in the gate and their full size under `IDLIN_LONG=1` in the capture workflow, which is not required.                                                                                                         | Every sweep at full size in the gate.                                                           | Every builder and reviewer waits on the gate several times per pull request. The full sweeps still run on each push to `main`, and a failure is a bug. |
| When `main` moves after a squash, the conductor re-squashes the branch itself, in a worktree of its own.                                                                                                                                                                     | Starting a builder for each re-squash.                                                          | A re-squash is a scripted block with no building in it; waiting for a builder slot to run it delayed merges.                                           |
