# 0015: When the session refreshes the lock, and a check before taking an old one

Date: 2026-11-26. From #261: a scheduled run found the session's lock 173
minutes old while the session was still merging and its builders were still
pushing. Section 0 said the session rewrites the time "at each step", which
did not say when. Changes section 0 of `process/cycle.md` and steps 2 and 3 of `process/daily.md`.

| Decision                                                                                                                                                                                                                                                                | Rejected alternative                                                                        | Why                                                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| The session rewrites the lock time after each merge, each time it starts a child task, and before it ends a turn to wait on children.                                                                                                                                   | "At each step", as before.                                                                  | Named points are easy to follow. The longest gap is then one wait on children, and a builder or reviewer rarely runs past 150 minutes. |
| A scheduled run or the digest that finds an old lock also looks for a role-tagged comment or a push to any branch in the last 150 minutes, and reports busy if it finds one. A session waiting on its children posts nothing itself, but its builders and reviewers do. | Trusting the lock's time alone; counting only `[conductor]` comments and commits on `main`. | A missed refresh then costs one skipped scheduled run instead of a second conductor starting builders beside the first one's.          |
| A scheduled run starts every post with `[conductor] (scheduled run)`, and those don't count as activity.                                                                                                                                                                | Counting every `[conductor]` comment.                                                       | A scheduled run that reports something on an issue would otherwise keep a dead session's lock alive.                                   |
